# Performance model for the condensation path

## Overview

This folder builds a simple performance model for the CLEO condensation microphysics path. The goal is
not to measure the full production code exactly, but to estimate the amount of arithmetic and memory
traffic generated by the algorithm so we can reason about its performance using a roofline model.

The model follows the actual control flow of the code. In a timestep, the model executes:

```text
run_step()
│
└── sdm_microphysics()
    │
    ├── GBx 0
    │    │
    │    └── microphysics.run_step()
    │         │
    │         └── condensation.run_step()
    │              │
    │              ├── superdroplets_change()
    │              │   │
    │              │   ├── saturation_pressure()
    │              │   ├── supersaturation_ratio()
    │              │   ├── diffusion_factor()
    │              │   │
    │              │   └── for each SD
    │              │       │
    │              │       └── superdrop_mass_change()
    │              │           ├── condensate_mass
    │              │           ├── kohler_factors()
    │              │           ├── solve_condensation()
    │              │           ├── change_radius()
    │              │           ├── calculate_mass_change()
    │              │           └── multiplicity
    │              │
    │              └── effect_on_thermodynamic_state()
    │                  └── thermodynamic_state_change()
    │
    ├── GBx 1
    │    └── ...
    │
    └── GBx N
         └── ...
```

Every function in this tree receives a `Workload` object which aggregates:

```text
Workload
│
├── operations
│     ├── "+"
│     ├── "-"
│     ├── "*"
│     ├── "/"
│     ├── "fma"
│     ├── "sqrt"
│     └── "exp"
│
├── bytes_read
└── bytes_written
```

The `Workload` is intentionally simple: it is a bookkeeping object for the total arithmetic and data
movement of one model step.

## Arithmetic model

The arithmetic side counts the scalar floating-point operations used in the condensation equations.
We count operations such as:

- `+`
- `-`
- `*`
- `/`
- `exp`
- `sqrt`
- `fma`

These are aggregated into a total FLOP count. We do not count compile-time constants, literals, or
local temporary expressions if they are not materialised in memory. In other words, we count the ops
that are conceptually part of the algorithm rather than every intermediate register operation.

This is a useful first-order approximation because it maps directly onto the roofline model.

## Memory traffic model

The memory model is intentionally conservative and naive. We assume:

- every scalar loaded from memory is one `double` transfer: 8 bytes
- every scalar written back is one `double` transfer: 8 bytes
- temporary arithmetic intermediates do not count unless they are explicitly stored or reused across
  function boundaries
- no cache, no vector reuse, no array-alignment effects are modelled here

This is a lower-bound, roofline-style approximation of the movement between main memory and the
arithmetic units. It is meant to be transparent and useful, not to reproduce the exact behaviour of a
modern memory hierarchy.

### Examples

- `saturation_pressure(temp)`
  - read: `temp` -> 8 bytes
  - write: `psat` -> 8 bytes

- `thermodynamic_state_change()`
  - read the relevant state scalars (`press`, `temp`, `qvap`, `qcond`)
  - write updated state values back to memory
  - we do not count every local algebraic temporary as an extra memory transaction

## Outputs

Each `Workload` object exposes:

- `workload.naive_FLOPs()`
- `workload.naive_RW_bytes()`
- `workload.arithmetic_intensity()`

These are then used to estimate the roofline position of the condensation kernel.
